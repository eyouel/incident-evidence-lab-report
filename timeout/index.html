Public completion policy
Public investigation-completeness-v1 is a new bounded workflow policy, separate from proposal format, claim support and independent diagnostic grading.
For an unknown outcome, first obtain a complete permitted source inventory. Account for each visible logs, traces and status source. These three kinds define this policy's bounded outcome-reading obligations, not every possible place an outcome could appear. Metrics, changes and pipeline sources create no mandatory reads.
A logs or traces check requests this operation over the complete incident start..cutoff window with limit 1..32. A status check requests this operation as_of cutoff. The status reader returns only its latest observed snapshot; this is not a complete status history. A valid full request with a complete empty or record-bearing response accounts for that reader's bounded check. Narrow, truncated, invalid or wrong-scope reads do not. Do not combine arbitrary partial pages to claim full coverage.
Known unavailable, denied, uncollected, out-of-retention or not-yet-available evidence is an access limit, not an empty read. Returned collection and retention boundaries can limit the window even when truncated is false. Fully blocked public inventory metadata may establish an access limit without a useless read. Partial collection or retention still requires checking the available portion through a full scoped request. Partial or missing inventory cannot establish that all sources were accounted for.
An existing adapter-and-claim-checker-accepted known outcome may stop without reading every source. An unknown proposal may also complete this procedure when legitimate returned observations for this operation and cutoff establish both completed and failed terminal outcomes. That conflict exception does not require a schema-valid unknown proposal, but the proposal must still pass the separate validators before workflow success. Either exception can use a legitimate returned witness from any source kind.
Otherwise, account for all declared obligations. A later valid complete read can finish an earlier partial check; earlier attempts remain recorded. Access or actual execution limits leave a separate limited workflow result. Model claims about exhausted budgets are not trusted counters. A next_check is only a suggestion, never a read. The model chooses every evidence request and its own answer; the host does not prefetch, repair answers or prescribe a diagnosis.
Completion means this finite public procedure was satisfied. It does not prove that all possible evidence exists here, that every returned fact was understood, or that the diagnosis is correct.

What someone else would need

Another application must declare what accepted, completed, failed and pending mean, expose permitted readers and supply independently established outcomes. Authorized local source access, Python3.12 with pinned dependencies and Docker are needed for this implementation; model execution additionally uses the already-installed Ollama0.33.3 and pinned Qwen3 model. No-account fixture and fixed-rule checks need no model. Historical replay additionally needs its saved local captures; the public site alone cannot reproduce private source execution. The implementation repository is private. This public site provides inspectable static records; it does not offer anonymous source access or run investigations. Suggested next checks are text, not executable controls.

The existing project methods acknowledge observability, bounded tool use, evidence reduction and diagnostic regression work. This implementation contributes an inspectable local experiment and strict host boundaries with measured failures; it does not claim globally unique invention.
