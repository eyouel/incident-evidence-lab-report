What actually happened

The model independently asked for an inventory and a status record, then reported the returned dispatch code with its record reference. On a separate supplied-observation task, it also reported the requested value correctly. These are useful, limited demonstrations.

In the four incident checks, it found a completion witness correctly once. It then invented a dependency location for a recorded failure. In both uncertainty cases it inspected only an acceptance record, skipped the remaining logs, and claimed completion. The trusted checker rejected those three proposals.

The failed gate stopped the next stage. All 16 development-regression slots remain unattempted. No fresh Java capture or new Java model trial ran. No expected answer filled an unused slot.

The correction and the failed candidates

The original native template inserted a Go-style function value inside a JSON wrapper. The HTTP response was valid JSON, but the declaration inside the rendered prompt was not. The project alias changes only the tool expression from {{ .Function }} to {{ json .Function }}. The pinned runtime provides this JSON helper. This is a local correction, not a claimed upstream release fix.

A shortened format example is {"type":"function","function":{list_sources ...}}; the corrected declaration contains a quoted "name" property inside a valid JSON function object. The strict inventory comparison still checks names, parameter definitions, and required fields. Full host validation retains constraints the runtime schema omits.

How this works

  1. The application or synthetic fixture provides a public operation contract and cutoff.
  2. A fresh isolated investigator asks for permitted evidence. The model has no shell, filesystem, repository, oracle, credential, or network tools.
  3. The trusted broker enforces source, operation, time, query and byte limits. It returns the actual observations.
  4. The model submits a proposal. The host checks its arguments and citations without changing them.
  5. A separate evaluator compares the accepted claim with established outcomes. Reports keep that score separate from format acceptance and model uncertainty.

The two small tasks used a direct trusted-host loop; the four incident cases used the pinned isolated Docker investigator. Native chat preserves actual assistant tool calls and tool-role replies. submit_diagnosis ends the investigation; it is not an eighth evidence reader. No final-answer grammar constrains native tool selection. The original seven readers, frozen expectations and historical cutoffs remain unchanged.

Measured effort and limits

64 application-to-runtime HTTP attempts: 25 metadata, 2 alias-creation, 8 render-only, and 29 generations. Reported usage: 98,898 prompt-evaluation tokens and 2,007 generated tokens; 267.66 seconds of aggregate runtime-reported duration for those generation requests.

The model requested 17 broker reads: 8 inventories, 8 reads returning observation records, and one unavailable-source read. These returned 14,642 serialized response bytes. Supplied interpretation preludes are counted separately in the records.

The shared clock stopped at 1021.56 seconds. It includes setup and offline work, so it is a conservative bound on runtime activity. Token totals include repeated context; bytes include response envelopes. Neither measures unique information or money saved. Underlying runtime HTTP activity and electricity, hardware and operating cost remain unknown.

Used limits: sequential local execution, 2,048 output tokens per request, 32,768 context tokens, 120 seconds per request, 300 seconds per investigation. The parent ceiling was four candidates, 640 generations, 1,600 HTTP attempts and four hours; no counter was reset. Two setup failures were preserved: a protected blob timestamp write, then an overly strict comparison of provenance and parameter ordering. The corrected setup reused unchanged local weight bytes.

What remains unverified

The complete evidence-removal/restoration AI demonstration is not complete. Native evidence access and one small interpretation task passed, but appropriate uncertainty and the complete incident gate did not. The 16 comparisons, fresh Java model views, policy advantage, general reliability and production adoption remain unestablished.

The demonstrated engineering decision is to keep the evidence checker and uncertainty gate in front of downstream claims. Valid JSON, successful tool use, and a correct outcome field can still accompany an unsupported answer.
